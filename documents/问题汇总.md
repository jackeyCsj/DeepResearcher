

##  一、项目整体架构

**介绍一下项目**

背景：我们研究生在需要对某个研究方向进行调研时需要花费大量时间精力去寻找文献并阅读，于是就想了做一个自主多 Agent 深度研究系统，主要解决复杂问题下人工检索效率低、信息分散以及报告缺少可靠引用的问题。  

用户输入研究问题后，系统会由Classifier先进行问题澄清，再由 Supervisor 将任务拆解成多个子问题，Researcher 并行调用网页搜索、学术搜索和本地知识库进行检索，之后由 Supervisor 根据证据质量进行审核，不合格的结果会自动重试或重新规划，最后由 Writer 生成带引用的结构化研究报告。 ，并且将报告写会RAG知识库。

技术上，后端使用 Python、FastAPI 和 LangGraph，前端使用 Next.js；本地知识库采用 BM25、向量检索和 Cross-Encoder 重排序组成的混合 RAG，并通过 MCP 统一接入外部工具。项目中我重点解决了多 Agent 状态编排、上下文长度控制、工具调用容错和实时流式展示等问题。

1. **为什么要设计多个 Agent，而不是一个大模型直接完成？**  
    可以回答：
    
    > 通过角色拆分降低单个 Agent 的任务复杂度；Researcher 可以并行执行不同方向，Supervisor 负责统一规划和质量控制，Writer 负责最终整合。
    
2. **LangGraph 在项目中解决了什么问题？**  
    重点说：
    
    > 用状态图管理 Agent 节点、状态传递、并行分发、条件路由、重试和重新规划，避免手动维护复杂的调用流程。
    
3. **Supervisor 和 Researcher 分别负责什么？**
    
    - Supervisor：拆分任务、分发子问题、审查研究笔记、决定通过/重试/重新规划。
    - Researcher：针对具体子问题调用 RAG、网页搜索、论文搜索等工具并生成研究笔记。
4. **Researcher 拿到的是原始问题，还是具体任务？**  
    应回答：
    
    > 拿到的是 Supervisor 拆解后的、范围明确且相对自包含的子问题，每个子问题本身就是一个完整研究任务。
    

### 二、RAG 和检索

6. **RAG 在整个流程的哪个阶段使用？**  
    这是很可能被问到的问题：
    
    > RAG 不是用户提问后的统一前置检索，而是 Researcher 的一个工具。Supervisor 拆解子问题后，Researcher 优先调用 `rag_search` 查询本地知识库，资料不足时再调用外部搜索工具。
    
7. **RAG 的完整检索流程是什么？**
    
    > 文档切块并向量化；查询时分别进行 BM25 关键词检索和向量检索，合并得到候选片段，再用 Cross-Encoder 对查询和候选片段进行相关性打分和重排序，最终将 Top-K 片段交给 Researcher。
    
8. **为什么使用 BM25 + 向量检索？**
    
    - BM25 擅长精确匹配关键词、术语和数字。
    - 向量检索擅长匹配语义相似内容。
    - 两者结合可以提高召回覆盖率。
9. **Cross-Encoder 在哪里使用？为什么不直接使用向量相似度？**
    
    > 初步召回后使用 Cross-Encoder 对候选片段进行二次排序。它把“问题 + 文档片段”联合输入模型，直接预测相关性，通常比单独比较向量相似度更准确，但计算成本更高，所以只处理候选集。
    
10. **本地知识库中保存哪些内容？**  
    可以回答：
    
    > 支持 PDF、Markdown 和 arXiv 文献；生成的研究报告也会自动写回知识库，便于后续研究复用。
    
11. **如何避免 RAG 检索结果太多导致上下文超限？**  
    说明：
    
    > 先限制候选数量和最终 Top-K，再对工具结果做截断；同时通过上下文压缩和历史压缩控制 Agent 的上下文长度。
    

### 三、工具调用和 MCP

12. **为什么引入 MCP？**
    
    > 将搜索、论文检索、网页抓取、文件转换等外部能力统一封装成工具，Agent 通过工具 Schema 动态调用，降低业务逻辑和具体工具实现的耦合。
    
13. **Researcher 如何决定调用哪个工具？**
    
    > 模型根据子问题和工具描述自主选择；提示词中还进行了成本分级，优先使用搜索摘要和本地 RAG，只有摘要不足时才升级到网页全文抓取或论文阅读。
    
14. **Brave 和 Tavily 的搜索源回退怎么实现？**
    
    > 对外暴露统一的 `search` 工具，当前代码是 Tavily 优先；如果 Tavily 异常或返回空结果，就切换到 Brave。两个适配器还会把不同返回格式统一成相同的搜索结果结构。
    
15. **MCP 工具重试是怎么做的？**
    
    > 针对 MCP 并发调用可能出现的 `already borrowed` 错误，最多重试 3 次，并采用递增等待时间。重试耗尽后抛出 `ToolCallError`，由 Researcher 将错误作为工具结果继续后续推理。
    
16. **工具调用失败会不会导致整个任务崩溃？**
    
    > 不会直接让整个流程崩溃。工具层返回错误信息，Researcher 可以根据错误继续尝试其他工具；搜索层还具有备用搜索源。
    

### 四、结构化输出和模型兼容性

17. **为什么要使用 JSON Schema 或 Function Calling？**
    
    > Supervisor 的规划和审查结果需要被程序继续处理，使用结构化输出可以稳定获取 `sub_questions`、`verdict` 等字段，避免从自然语言中猜测结果。
    
18. **千问模型能不能支持这种结构化输出？**
    
    > 千问的 OpenAI 兼容接口通常支持 Tools/Function Calling。项目通过 `tools` 和 `tool_choice="required"` 约束模型调用指定函数，同时保留文本解析和 JSON 修复作为兼容方案。
    
19. **如果模型没有按照 Schema 返回怎么办？**
    
    > 先尝试读取标准 `tool_calls`；如果模型直接输出文本，则去除 Markdown 代码块和函数名前缀，再使用 `json.loads`；解析失败时通过 `json_repair` 修复，必要时重新请求一次。
    
20. **Researcher 的工具调用格式不规范怎么办？**
    
    > 如果模型没有返回标准 Tool Call，但输出了类似 `rag_search({...})` 的文本，系统会通过正则提取工具名和参数，构造内部调用继续执行。
    

### 五、质量控制和容错

21. **Supervisor 如何判断研究结果是否合格？**
    
    > 从相关性、研究深度、引用完整性、来源质量/多样性、内容完整性等维度审查，并输出 `approved`、`retry` 或 `revise`。
    
22. **`retry` 和 `revise` 有什么区别？**
    
    - `retry`：当前子问题方向基本正确，但研究深度、引用或来源不足，重新执行该子问题。
    - `revise`：整体研究计划存在遗漏，需要 Supervisor 重新拆分或补充子问题。
23. **最多会重试几轮？为什么要设置上限？**
    
    > 默认最多 3 轮，防止低质量结果导致无限循环，同时控制 API 成本和整体延迟。
    
24. **如果某个 Researcher 失败，其他 Researcher 会受影响吗？**
    
    > Researcher 之间相互隔离、并行执行；单个工具或子任务失败时，通常只影响对应研究笔记，Supervisor 可以针对该任务重试或重新规划。
    

### 六、工程实现

25. **SSE 在项目中是怎么使用的？**
    
    > FastAPI 以 SSE 方式持续输出 LangGraph 节点事件，前端实时接收计划、研究、审查和报告生成状态，不需要等待整个任务完成后一次性返回。
    
26. **为什么不用普通 HTTP 一次性返回？**
    
    > 深度研究耗时较长，一次性响应用户无法知道进度；SSE 可以实时展示当前阶段和工具调用结果，改善交互体验。
    
27. **如何控制上下文长度和 API 成本？**
    
    > 使用 Token 计数、历史压缩、工具结果截断和上下文预算；同时按工具成本分级，优先调用低成本摘要工具，必要时才进行全文抓取或论文阅读。
    
28. **项目中最难的技术问题是什么？**  
    推荐回答：
    
    > 难点主要是多 Agent 状态编排、并行任务结果汇总、不同模型的工具调用兼容，以及外部 MCP 服务的不稳定性。通过 LangGraph 状态管理、结构化输出兜底、搜索源回退和工具重试解决。
    

### 七、个人贡献和项目反思

29. **你在项目中具体负责什么？**  
    可以结合实际情况回答：
    
    > 我主要负责多 Agent 研究流程设计与实现、LangGraph 状态图编排、混合 RAG 检索和重排序、MCP 工具接入，以及搜索回退、工具重试、结构化输出解析和 SSE 流式交互。
    
30. **项目目前有什么不足？**  
    不要说“没有不足”，可以回答：
    
    > 目前主要依赖模型进行工具选择，检索和生成还缺少系统化的离线评测；后续可以增加 Recall@K、MRR、引用准确率、报告完整性和端到端延迟等指标，并进一步优化缓存、并发控制和权限隔离。
    
31. **如何证明项目效果？**  
    如果目前没有正式数据，不要虚构指标：
    
    > 当前项目重点完成了端到端功能和容错链路，尚未建立完整的基准数据集。后续会构造固定问题集，对混合检索、重排序、引用准确性、任务成功率和响应延迟进行对比评估。

## 记忆机制设计总结

这个项目的记忆分**短期（会话内）**​和**长期（跨任务）**​两层：

### 1. 短期记忆：每个 Agent 独立的 `_history`

定义在 `client/base/agent.py`（`self._history: list[Message]`），由 `ContextBuilder`（`client/context/context_builder.py`）在每次调 LLM 时组装进上下文，并按 token 预算做**两级压缩**（`client/context/history_compactor.py`）：

- **常规压缩 `compress_old_rounds()`**：Researcher 每步 ReAct 前检查，历史 token 达到可用预算的 **40%** 就触发。按 assistant tool call 识别旧轮次，只保留最近 1 轮完整观察，把旧的、超过 500 字符的工具结果**一次 LLM 调用批量压缩**，原位替换为 `[Compressed] Tool: xxx | Args: xxx + 摘要`。
- **兜底压缩 `summarize_all()`**：历史超过总预算（`max_tokens=30000` 的 85%，即扣除 15% reserve 后）时，把整段历史压成一条 `[Compacted]` 用户消息。

配套细节：普通工具结果超 2 万字符截断；`fetch` 抓的网页先去噪再截断到 1 万字符。另外每个 Researcher 由工厂临时创建，**子问题之间历史天然隔离**，互不污染。

### 2. 长期记忆：复用 RAG 知识库（没有独立记忆库）

- 最终报告在 `write_node` 里通过 `pipeline.add_text()` **自动回存**到 `data/search_cache/`，并进入 `data/vector_store.json` 索引（分块 500/重叠 100 → embedding → BM25+cosine 混合检索 + CrossEncoder 重排）。
- 后续研究任务中，Researcher 可用白名单工具 `rag_search` 检索这些历史报告和导入的文献，形成“报告回存 → 检索复用”的闭环。
- 持久化全靠文件系统（JSON + Markdown 目录），没有数据库服务。
