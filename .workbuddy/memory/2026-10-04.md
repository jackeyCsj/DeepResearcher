## 诊断："登录不上" = 后端 startup 还没跑完（不是登录坏了）

**现象**：用户 `python server.py` 后前端登录失败，终端日志停在 jieba 加载。

**结论：登录链路本身完全正常，是启动时序问题。**

排查证据（全部实测）：
- 后端在跑：`0.0.0.0:8001` LISTENING，`GET /openapi.json` → 200，耗时 47ms。
- PostgreSQL `5432` 正常监听。
- 登录接口正常：用不存在的用户 POST `/api/auth/login` → **401**「用户名或密码错误」（不是 500/超时）。
- 用户记录完好：`users` 表有 `csj`（有 password_hash）。
- 鉴权链路通：用 auth 模块给 csj 生成 token 打 `/api/auth/me` → **200**。
- 认证实现无问题：pbkdf2_sha256 + JWT HS256，有效期 10080 分钟（7 天）。

**真正的瓶颈**：startup 耗时约 **53 秒**。日志时间线：
`00:07:04` 启动 → `00:07:05` 跳过 brave-search → **`00:07:50` `fetch` 服务超时 45 秒被跳过**
→ `00:07:51` paper-search → `00:07:56` github 连完。
`fetch` 配置是 `"command": "uvx"` + `mcp-server-fetch`，而它的 env 里显式写了 `"all_proxy": ""`
（清空代理）→ uvx 直连 PyPI 解析/下载包，网络慢时卡满 45 秒 connect_timeout。
`uvx.exe` 位置：`D:\miniconda\envs\deep_research\Scripts\uvx.exe`（后端能找到）。
`.env` 里的 `http_proxy`/`https_proxy` 是**注释掉**的。

**旁证**：`logs/` 里有 `00:03:29`、`00:06:00`、`00:07:04` 三次启动日志 → 用户等不及反复重启。

**给用户的建议**：等终端出现 `Application startup complete.` 再操作；
想加快可任选：① 预热 `uvx mcp-server-fetch`；② 给 fetch 配上代理；
③ 在 `configs/mcp_servers.json` 里把 fetch 设 `"enabled": false`（但 researcher 的
allowed_tools 里有 `mcp__fetch__fetch`）。

**启动慢别急着 Ctrl+C**：MCP 连接 + 首次 npm 安装是正常耗时，看到
`Application startup complete.` 才算就绪（uvicorn 的这行只打终端，不写 `logs/*.log`，
该目录是项目自己的 logger 写的）。
