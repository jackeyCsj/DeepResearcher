## 修复：server.py 启动卡死（无任何日志）

**现象**：conda 环境 deep_research 下 `python server.py` 启动后终端长时间无任何输出，看似"启动不了"。

**根因**：`server.py` 中 `uvicorn.run(reload_excludes=["data/*", "data/**", "logs/*", "logs/**", "web/node_modules/*", "web/node_modules/**"])`。
uvicorn 0.40 的 `config.resolve_reload_patterns()` 对非目录的 pattern 会执行 `Path.cwd().glob(pattern)`：
- `data/**` 展开 3639 个子目录、`web/node_modules/**` 展开 2371 个子目录，共约 6100 个；
- 随后对每个目录做 `resolve()` + `is_dir()`，再跑 O(n²) 父子目录去重循环（约 1800 万次比较）；
- 实测在 `Config(...)` 构造阶段就卡死 >7 分钟不返回，因此连 `Will watch for changes` 都打印不出来。

**修复**：`reload_excludes` 改为目录名形式 `["data", "logs", "web/node_modules"]`（不带通配符）。
uvicorn 对目录名走 `is_dir()` 快路径直接加入，不触发 glob 展开。修复后正常打印
`Uvicorn running on http://0.0.0.0:8001` 并 `Application startup complete`。

**教训**：给 uvicorn 的 `reload_dirs/reload_includes/reload_excludes` 传 `**` 通配模式是危险的，
一律写目录名。另外 `reload_dirs` 已限定为 `["client", "configs"]`，这些 excludes 本身是多余的。

## 前端报错 `Runtime TypeError: Failed to fetch` at clarify（已修 + 待观察）

**现象**：研究进行中切到别的对话 → 切回后该对话卡住 → 开新对话提问时报
`Failed to fetch`，栈指向 `lib/api.ts:95 clarify` ← `ClarifyPanel.tsx:67 useEffect`。

**排查结论**：
- 后端是健康的：`POST /api/clarify` 无 token 正确返 401，`/openapi.json` 3ms 响应；
  路由存在、CORS `allow_origins=["*"]`；`client/`、`configs/` 在研究期间无任何文件改动，
  排除 uvicorn reload 自动重启；后端仍存活（PID 13628，0.0.0.0:8001）。
- **真正的坑（已修）**：`ClarifyPanel` 的 useEffect 里 `clarify(query, token).then(...)`
  **没有 `.catch()`**，任何网络层失败都变成 unhandled rejection，被 Next.js dev overlay
  捕获后显示成 `Runtime TypeError: Failed to fetch`（看起来像崩页，其实只是单次请求失败）。
- **切换会话的设计缺陷（已部分修）**：`handleSelectSession` 只把 stage 设为 "input"，
  既不 abort 后端任务也不提供恢复入口，切回后渲染只读的 HistoryMain → 表现为"卡住"；
  而且没清 `_clarifyCache`（模块级单例）→ 缓存跨对话残留。已在切换时加 `resetClarifyCache()`。

**另一半"卡住"的原因（未修，待查）**：日志显示该研究任务停在
`19:50:41 [Graph] route: 全部通过, 进入 write` 之后**10 分钟无任何输出**，
即 `write` 阶段本身挂住了（疑似 LLM 调用挂起）。后端 `/api/research`、`/api/clarify`
都是同步 `def`（跑线程池），abort 只断前端连接，后端任务会继续跑成僵尸任务。

**待办**：查 `write_node` 为何不产出日志；考虑把长任务改 async 或加取消机制。

## 修复：提问后侧栏出现两个会话（StrictMode 双调用）

**现象**：提一个问题，侧栏冒出两个会话条目，多出来的那个只有首轮 user query + 首轮 assistant 回答。

**根因**：Next 16 / React 19 未配 `reactStrictMode` 时**默认为 true**，dev 模式下每个
useEffect 会 mount→cleanup→mount 执行两次。`ClarifyPanel` 的 effect 直接发 `clarify()`，
且**没有 AbortController**（`cancelled` 只是丢弃结果，请求照样发出），
后端 `/api/clarify` 每次都 `create_session` → 第一个会话成为孤儿，
后续 research 用的是第二次的 session_id，所以孤儿会话停在首轮问答。
（同步 `def` 路由感知不到客户端断开，加 AbortController 也拦不住后端建会话，必须从前端去重。）

**修法（用 ref 守卫，StrictMode 双调用是同一 fiber 实例，useRef 值会保留）**：
- `web/components/ClarifyPanel.tsx`：加 `requestedRef`，`if (requestedRef.current === query) return;`。
- `web/components/ResearchProgress.tsx`：同样问题会让**研究真的跑两遍（双倍 token）**，
  加 `startedRef`，key 用 `${sessionId ?? ""}::${brief}`。

**注意**：不要为了绕开它去关 `reactStrictMode`，那会掩盖其他问题。dev 双调用只在开发环境出现。

### 更正（重要教训）：ref 守卫方案引入了回归，已撤销

上一轮给两个组件加的 ref 守卫**是错的，已全部移除**：
- `ResearchProgress`：StrictMode 第一次 effect 发起请求 → cleanup 执行 `abort()`
  把流打断 → 第二次 effect 因守卫直接 `return` → **再也不发请求**，研究根本不启动，
  表现为"不实时显示调研进度"。
- `ClarifyPanel`：同样的结构会让第一次请求的结果被 `cancelled` 丢弃、
  第二次又不发请求 → 永远卡在"正在分析问题"。

**教训**：在"cleanup 会 abort / 丢弃结果"的 effect 上，单纯加 ref 守卫必然互相冲突——
第一次被 abort，第二次被守卫挡住。要让守卫成立，必须让第一次的结果仍被采用
（如模块级 in-flight promise 缓存），或让第一次不被 abort。别只加 ref。

**最终方案**：`web/next.config.ts` 设 `reactStrictMode: false`（并写明原因），
从源头消除双调用。研究是昂贵且非幂等的长任务，与 StrictMode 的双调用语义根本冲突。
改 next.config 必须**重启 dev server** 才生效（组件改动 HMR 即可）。
