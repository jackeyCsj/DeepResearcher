## 复盘：各 agent 的上下文构成（对照"工作区重构"面试模板）

代码依据：`client/base/agent.py`（_history + _build_messages）、`agents/*.py`、`context/context_builder.py`。

四个 agent 的实际上下文构成：
- **Clarifier**：无 _history，analyze / refine 两次调用各自独立拼 messages。最轻。
- **Supervisor**（graph 内单例，跨所有超步复用）：system + 长期记忆 + research_brief（锚点）
  + **累积的 _history**：每次 plan/review 都 append user+assistant(tool_call)+tool(result)，
  而 review 的 user prompt 里含**全部待审笔记全文**，且永久留在 history 里。
- **Researcher**（每个子问题/重试新建实例，history 天然隔离）：system + 长期记忆 + 子问题
  + ReAct 轮次（assistant 推理 + tool 结果，单条 ≤20000 字符，fetch 走 denoise ≤10000）。
- **Writer**（单例，只调一次）：system + 长期记忆 + brief + 全部 approved notes，无 ReAct。

与原图面试模板的差异（重要，可作为项目特色话术）：
- 第 1 点"架构隔离"完全成立：跨 agent 只传子问题与压缩后的 note，主 agent 不拿检索原文。
- 第 2 点"工作区重构"实现路线不同：项目是 **append + 阈值触发压缩**（40% 触发
  compress_old_rounds 把旧 tool 结果原地替换为 [Compressed] 摘要；超 85% 用 summarize_all
  把整段 history 换成一条 [Compacted]），不是每步替换式工作区。
  后果：上下文在预算区间内锯齿波动，平均近似线性，而非收敛到常数。
  keep_recent=1 对应模板第 3 点"最近一次交互结果"；任务锚点靠每轮 prompt 重新注入
  （researcher 的 retry prompt 带 sub_question，review prompt 带 research_brief）。

## 发现的风险点（待评估）

`Supervisor` 是项目里上下文增长最快的 agent，且**没有轮次隔离**：第 n 轮 review 的输入
会把前 n-1 轮 review 的全部笔记重新发一遍，输入量随轮数近似 O(n²)。
`context_builder` 只有超预算兜底，没有对 review prompt 本身做历史裁剪。
可考虑：review 完成后清理/摘要化旧的 review user 消息（类似工作区替换），
或让 supervisor 不复用 history。

## 多轮对话改造分析（用户问：第二轮追问 Clarifier 能否理解）

结论：**不能**。证据链：
- `api/app.py:99` `clarifier.analyze(body.query)` 只传原始字符串；
- Clarifier 不继承 AgentBase，无 _history、无 context_builder（连长期记忆都没有）；
- DB 里的 session 消息（brief、user 反馈）只用于前端展示，从未回流给 agent；
- 第一轮报告存盘后（`/api/reports/{id}`），其内容不进入任何后续轮。

两条改造路线（已告知用户）：
1. 最小改：/api/clarify 接 session_id，从 repo 取上一轮 brief + 报告大纲注入 prompt
   （报告全文别塞，用章节标题/摘要）。缺点是产出的新 brief 走全量重跑，成本同首轮。
2. 推荐：把用户反馈解析成 revision_points / missing_dimensions，**复用
   SUPERVISOR_REPLAN_USER 的既有 replan 机制**（本就支持 approved_questions +
   revision_points，只是目前触发源是 LLM 评审），已通过笔记直接复用，只调研缺口，
   天然是 human-in-the-loop 的补充形态。
